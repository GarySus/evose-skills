# Lark 通知与双向交互

业务专用CLI/Skill为按需依赖，非安装本包的前置。Evose管理权限、Lark开发者权限、本机CLI授权与云端Agent工具连接分别核对。

## 先读现状

1. 当前部署组织管理 → 集成 → IM应用，候选路径 `/system/integration/im-apps`。有权限就继续；菜单没入口只是线索，实际返回无权限时再请相应管理员开通，不猜角色或绕过校验。
2. 对照平台、组织、App ID、入站方式、在线状态与授权范围。显示名能变化，用App ID/open_bot_id核对群发送者。Secret仅由用户在正常授权界面输入，不复制或记录。
3. 区分独立群策略与默认策略，核对目标Agent、自动回复、携带历史、使用权限、私聊方式与成本归属。只读时取消查看草稿，不提交。
4. 先读已有真实消息、reply_to/thread_id和时间，再在观测追踪按IM来源找实际会话，核对主Agent、子调用、版本、参数与成果。不要为排查重复发探针。

## 配置语义

以下为历史UI说明，当前界面优先，不把原项目设置当默认值。

| 配置 | 需核对的含义 |
|---|---|
| 群独立策略 | 可能覆盖该群默认；单群测试不改其他群或全局路由 |
| 自动回复 | 历史开启表示群内每条消息触发；仅@模式另验 |
| 携带消息 | 不携带、本轮、本轮加最近消息不同；历史“最近”有时长与条数上限，不是无限长期记忆 |
| 使用权限 | 开放使用不等于有权确认永久写入；真实身份从可信元数据取得 |
| 私聊 | 独立会话与持续会话不同，历史持续模式用 `/new` 开新会话 |
| 成本归属 | 计入成员或机器人、身份是否关联、配额方案分别判断 |
| 应用连接 | 在线、长连接、权限齐备，不单独证明所有群/线程工作正常 |

Bot工具以应用身份操作，IM工具以授权用户身份操作。都显示“个人账号”也不证明主体相同。挂载后仍检查工具授权及实际连接App ID，不能用本机另一个Bot代发来验收指定应用。

## 三类链路分别验收

| 目标 | 真实链路 |
|---|---|
| 定时通知 | 计划 → Agent → 已授权发送工具 → 目标群 |
| 群消息触发 | 原生接收/事件 → 正确Agent及上下文 → 原线程回复 |
| 卡片确认 | 卡片回调 → 身份、对象与版本校验 → 指定写入 → 回执 |

能查消息、能发送、能接收事件是不同能力。先复用Evose原生IM入口，不自行另起机器人或用轮询冒充实时。`app not online`曾对应接收端离线，不能靠增加发送方法修复。若检查Lark事件，核对当前 `im.message.receive_v1` 文档与长连接/回调真实日志。

## 用户体验逐项记录

- 接收和首卡延迟、首个有效内容延迟、执行总时长分别测量。分钟精度消息不能计算秒级延迟。
- 卡片创建后更新不等于持续正文流式；阶段状态与增量正文分别记录。
- 忙时追加要求要确认是排队、合并、接续或取消。历史单样本显示追加请求在旧任务完成后才处理，不支持忙时实时交互已通过的结论。
- 连续改稿可接续，不代表多用户、多话题隔离通过。核对真正成品与可用文件，不能只看追踪成功。

## 通知、幂等与归档

只发已有报告就复用冻结成果，不重采数据或重新生成。导出、回填链接、替换Base附件、群发送分别报告。IM资源上传不能自动当成Base附件归档。

发送验收保留真实主体、目标、调用次数、明确拒绝数、未知结果数、message_id，并按ID独立读回。历史uuid最长50字符报错属于该接口约束，长度由程序检查；省略幂等键后的送达不是可靠重试方案，未知结果先查送达。

“执行记录”文本更新曾只写新条目而覆盖历史，即使Agent自评追加成功。写前重读、保留原历史、核对payload及写后读回；文本读改写不提供原子追加。

机器人消息归档区分接收机器人与发布者身份，app_id、open_id、open_bot_id不能跨命名空间直接比较。同一应用可能发布多个产品，需可信卡片标题/版本辅助区分，不以共享app_id唯一映射产品。原始消息链接不能用GitHub Release链接替代。

空结果也要看内层items、has_more与实际窗口；外层success、表内查重命中不证明源消息已读。无新消息扫描通过不证明新消息插入成功或长期调度稳定。

Lark原文若引用嵌入表格，应继续读取真实工作表；安排没有进度列就写待核实，不能推断未完成。接口和附件操作按当前专用Skill处理。
